Executive Summary

1. Early release was real, but the first metric was too blunt

FM header rollout showed a visible failure mode: after grasping apricot, gripper command could reopen too early. The initial scalar probe drop > 8 over all future tokens over-counted normal place/release behavior. We later restricted the metric to closed_hold validation states and added sequence metrics such as sustained release run and tail collapse.

2. Gripper is a special action dimension

SO100 gripper distribution is long open/closed holds plus sparse transitions. This is unlike pose dimensions. Literature and LeRobot practice support treating gripper carefully: LeRobot defaults to absolute actions and explicitly excludes gripper from relative encoding because gripper commands are typically binary open/close.

3. Gripper 5x loss helped the release failure

The implemented intervention was action_dim_loss_weights: [1, 1, 1, 1, 1, 1, 5] for the FM head. On the refined closed-hold probe, FM gripper5x 80k reduced qf33 early release to zero unique closed-hold samples. In hardware rollout, the original “grasp then immediately release” failure was not observed after this change.

4. Remaining FM problem is pose/chunk consistency

After gripper loss was improved, FM success rate was still below MLP. Validation-state probes showed that FM can have competitive GT action error but worse chunk-to-chunk temporal consistency. With the latest official-style resample rollout metric, FM gripper5x 60k is still about 2.3x worse than MLP on position consistency and 2.8x worse on rotation consistency. This is evidence for a candidate failure mechanism, not proof that mean mm-level discontinuity alone explains rollout success.

5. Rollout time scale was mismatched

SO100 training reads a raw future action horizon of 30 and interpolates it into 100 action tokens. The old SO100 rollout used raw token stride selection. EgoVerse official rollout instead resamples predicted chunks to 45 and executes 30 steps before re-querying. We changed SO100 rollout to match that pattern.

Current conclusion

The official-style rollout and blend5_pose_only both improve command smoothness, and blend5 reduces real query-boundary pose jumps by about 5x. Since the blend5 hardware rollout still failed, temporal inconsistency is no longer the primary bottleneck. The latest log/video check points to approach/contact geometry plus gripper phase timing: the gripper reaches the closed threshold before a reliable capture, then later opens without a confirmed lift.

Gripper Early Release Investigation

What “early release” means in the refined probe

The useful validation set for this question is not all samples. It is a closed-hold subset where the current gripper is already closed and the ground-truth future sequence says it should remain closed.

closed_hold if:
  state_gripper >= 30
  min(gt_gripper_future) >= state_gripper - 3

release-like prediction if:
  state_gripper - pred_gripper > 8

The sequence version also checks whether release is sustained, where it starts, and whether the tail mean collapses. This matters because one isolated token just over threshold is much less serious than a long run of release commands.

Caveat from the investigation: drop > 8 over a long future horizon is not by itself a bug. In a pick-place task, later tokens may correctly open the gripper for placement. The more reliable target is closed-hold early release, especially early or sustained drops while GT is still holding.

Gripper 5x Loss Implementation

The implemented change is generic action-dimension weighting in the denoising/FM policy loss. Source: egomimic/models/denoising_policy.py.

loss = mse(pred, target, reduction="none")
loss = loss * action_dim_loss_weights
if normalize_action_dim_loss_weights:
    loss = loss / mean(action_dim_loss_weights)
return mean(loss)

Experiment config: train_zarr_so100_singlearm_fm_gripper5x_steps60k.yaml.

action_dim_loss_weights: [1, 1, 1, 1, 1, 1, 5]
normalize_action_dim_loss_weights: true
max_steps: 60000
valid_ratio: 0.1

Because normalization is enabled, the absolute loss scale is kept roughly stable. The average weight is 11/7 = 1.571, so the effective multipliers are approximately:

Dimension group Raw weight Effective weight after divide by mean Relative to non-gripper
xyz + yaw/pitch/roll 1 0.636 1x
gripper 5 3.182 5x

This is not a separate gripper head or a classification objective. It is the smallest intervention that kept architecture and data unchanged while forcing the FM objective to care more about gripper error.

External evidence and caveat

The broader evidence does not prove a theorem that diffusion/FM must be worse at grippers. It supports a narrower engineering point: gripper commands often have binary or long-hold structure, so treating them exactly like smooth pose dimensions can be fragile.

  • LeRobot action representation docs state that absolute actions are the default and that gripper commands are typically binary open/close and do not benefit from relative encoding: LeRobot Action Representations.
  • Diffusion Policy introduces action-sequence generation with receding-horizon control, which makes chunk execution details central to policy behavior: Diffusion Policy, Chi et al..
  • Recent flow/diffusion follow-up work explicitly targets streaming/tighter loops because sampling full trajectories before execution can be a bottleneck for receding-horizon control: Streaming Flow Policy.
  • A diffusion-policy component study also identifies action sequence execution and receding horizon as core components, matching our finding that rollout semantics are not a minor detail: Unpacking the Individual Components of Diffusion Policy.

Temporal Consistency Investigation

Metric definition

For two adjacent validation states from the same episode, at dataset indices t and t+1, let the predicted action chunks be:

P_t[0:H], P_{t+1}[0:H]

A receding-horizon policy is temporally consistent if the future plan from the first query agrees with the next query after shifting by one step:

consistency_error_i = P_t[i + 1] - P_{t+1}[i]

We summarize:

pos_consistency = mean_i || error_i[x,y,z] ||_2
rot_consistency = mean_i || error_i[yaw,pitch,roll] ||_2
z_consistency   = mean_i | error_i[z] |
grip_consistency = mean_i | error_i[gripper] |

Interpretation: official-style resampling is the right rollout semantics for this codebase, and it improves smoothness. It does not make FM behave like MLP. In the validation probe, FM still has a large relative receding-horizon continuity gap, especially pose and rotation.

Possible gripper-weight trade-off: gripper 5x loss improves closed-hold early release, but the percentile table suggests a possible cost in pose/rotation consistency. Compared with FM baseline 60k, FM gripper5x 60k has position p95 14.52mm vs 13.29mm, rotation p95 0.0811 vs 0.0745, position max 27.85mm vs 20.89mm, and rotation max 0.2398 vs 0.1673. This is not strict causal proof because the models are separate training runs, but it is a useful warning: increasing gripper loss may shift optimization pressure away from smooth pose chunk consistency.

Important caveat: the mean position discontinuity is not huge in absolute terms. For example, MLP 80k is 3.24mm and FM gripper5x 60k is 7.41mm under rollout_resample45_exec30. The extra mean gap is about 4.17mm, which by itself should not be treated as a complete explanation for failed pick/place. The more concerning parts are the tails and rotations: FM gripper5x 60k has position p95 14.5mm and rotation p95 0.081rad, while MLP has position p95 7.44mm and rotation p95 0.031rad. On closed_hold states, FM gripper5x 60k reaches position p95 17.4mm and rotation p95 0.089rad.

The next stronger test is not another averaged validation metric. It is to compute the actual executed command boundary jump in successful vs failed rollout logs: last executed command from chunk k versus first executed command from chunk k+1, after IK/safety clipping. That would directly answer whether chunk discontinuity is large at the hardware command boundary where failures happen.

Training Action Chunk vs Rollout Strategy

SO100 training chunk construction

SO100 embodiment defines ACTION_HORIZON_REAL = 30 and ACTION_CHUNK_LENGTH = 100. Source: egomimic/rldb/embodiment/so100.py.

raw future command window: 30
training target chunk:    100 tokens

The transform splits raw command pose/gripper, converts rotvec pose to yaw/pitch/roll, and interpolates both pose and gripper to chunk_length=100. Source: action_chunk_transforms.py.

InterpolatePose(new_chunk_length=100, mode="xyzypr")
InterpolateLinear(new_chunk_length=100, action_gripper)

Therefore, 100 model output tokens should not be interpreted as 100 native 30Hz control steps. They are an interpolated representation of a shorter raw command horizon.

EgoVerse official rollout behavior

The official/main rollout path uses:

DEFAULT_FREQUENCY = 30 Hz
QUERY_FREQUENCY = 30
DEFAULT_RESAMPLE_LENGTH = 45

It predicts a chunk, resamples it to 45 actions, executes action indices 0..29, then queries again. Source: egomimic/robot/rollout.py.

Old SO100 rollout behavior

Before the change, SO100 rollout selected raw chunk indices by:

action_indices = action_start_index + arange(query_frequency) * action_stride

With the common FM command:

--query-frequency 99
--action-start-index 1
--action-stride 3

the actual executed indices were 1,4,7,...,97, i.e. 33 actions. This approximated a time-scale compression, but it was a hard subsampling strategy rather than the official interpolation/downsample.

New SO100 rollout behavior

SO100 rollout now defaults to official-style resampling. Source: so100_hpt_receding_rollout.py.

DEFAULT_QUERY_FREQUENCY = 30
DEFAULT_RESAMPLED_ACTION_LEN = 45

pred chunk 100
  -> interpolate to 45
  -> execute first 30
  -> re-query

The interpolation is not “take every Nth token”. It maps old/new time grids:

old_time = linspace(0, 1, 100)
new_time = linspace(0, 1, 45)

For [x,y,z,yaw,pitch,roll,gripper], xyz and gripper are linear-interpolated. Euler angles are unwrapped before interpolation and wrapped back after interpolation.

Next rollout-side test: blend5_pose_only

The offline smoothing probe showed blend5_pose_only as the only rollout-side smoothing candidate worth testing on hardware. It blends the first 5 pose actions of the new chunk with the unexecuted tail of the previous chunk, while leaving gripper values untouched.

new_chunk[0:5, pose] =
  alpha * new_chunk[0:5, pose] + (1 - alpha) * previous_chunk[30:35, pose]
alpha = [1/5, 2/5, 3/5, 4/5, 5/5]

This requires a resampled chunk longer than the executed interval. Therefore blend5 should use resampled_action_len=45, query_frequency=30, not resampled_action_len=30. With 30/30, there is no previous tail to blend.

The SO100 rollout script now supports this via --rollout-blend-steps 5 --rollout-blend-dims pose. Logs include rollout_blend_info, rollout_blend_applied, rollout_blend_steps_applied, and pre/post boundary gap diagnostics.

Why the next suggestions focus on gripper: the logs do not prove that gripper is the only problem. They do show that pose boundary discontinuity can be largely removed without restoring success, while gripper commands still contain open bursts after a closed state. The previous resample30 run also showed a visible slip while the gripper was still closed, followed immediately by a model open command. So the next debugging target is better stated as grasp stability plus gripper hold/release behavior, not gripper alone.

Low-level execution check: in the blend5 approach window before sent gripper first reaches 30, only 9/56 steps had position clipping, all at startup or the first re-query (steps 0-5 and 32-34). The largest IK-to-safe joint change was at startup (25.3deg at step 0), but it was gone by step 8 (t=0.27s). From roughly 0.8s through the failed contact, target_pose_position_clipped=false and IK error is sub-mm to about 1mm. So the approach failure is unlikely to be explained primarily by rollout clipping or IK tracking.

Current interpretation: FM gripper5x did reduce the original immediate-release failure, but the real rollout still contains a different timing problem: the policy appears to use a fairly script-like close/hold/open schedule. If the side approach has not actually captured the apricot by the time the learned schedule reaches its open phase, the gripper opens and the policy loses the chance to recover. This is better described as approach/contact geometry plus no grasp-confirmation gate, not just closed-hold early release.
